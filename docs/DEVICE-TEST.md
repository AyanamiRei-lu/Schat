# 真机验证指南

> **关于本文档中的地址与路径**
>
> 本文档原为一台开发机的实测记录。为公开发布，其中的服务器地址已替换为示例地址
> `192.168.1.100`，项目路径已替换为 `<项目目录>`，证书指纹已替换为占位符。
> 命令可以直接照抄，但请把地址换成**你自己**服务器的局域网地址。
>
> **证书指纹必须来自你自己的服务器**（首次启动时会打印，或用 `--print-uri` 查看）。
> 不要使用本文档里出现过的任何指纹值——一个公开的指纹配上泄露的私钥，等于任何人都能
> 冒充那台服务器，而客户端只验证指纹。

> **这一版能验证什么**：身份生成（走 Go 协议核心）、口令 → 保险库创建（Argon2id + Keystore 包装）、恢复码生成与确认、服务器连接信息解析与存储、重启后的解锁，**以及单聊：连接中继、发布预密钥、建立会话、比对安全码、互发消息**。
>
> **这一版还验证不了什么**：群聊（步骤 6a/6b）与富媒体（步骤 7）；服务器配置二维码（步骤 3c，仍需手动粘贴 URI）。

## 1. 前置条件

- 手机 **Android 8.0 及以上**
- 开启"开发者选项 → USB 调试"（设置 → 关于手机 → 连点"版本号"7 次）
- 数据线，或能通过文件管理器把 APK 拷进手机
- 建议先记下手机 ABI：`adb shell getprop ro.product.cpu.abi` 应输出 `arm64-v8a` 或 `armeabi-v7a`

## 4. 双机对发验证（步骤 5 的关键证据）

这是步骤 5 **唯一尚未取得的证据**。上面第 3 节的清单只验证单机流程，这一节验证两台设备真的能通过自建服务器交换端到端加密消息。

需要：**两台安卓设备**（或一台真机 + 一台模拟器）、**同一局域网**、一台能跑 `schat-server` 的电脑。

### 4.1 启动服务器

```powershell
cd <项目目录>\server
$env:GOWORK='off'
go run ./cmd/schat-server --listen 0.0.0.0:8443 --name my-relay --state-dir .\state
```

它会打印一条 `schat://connect?...` —— **把整条复制下来，两台设备都要用同一条**。

- [ ] 打印的 URI 里有 `fp=`（64 位十六进制证书指纹）和 `ss=1`

> **如果打印的 `h=` 是 `localhost` 而不是局域网 IP**，手机就连不上。显式指定：
> `go run ./cmd/schat-server --listen 0.0.0.0:8443 --public-host 192.168.x.x --name my-relay --state-dir .\state`
> 用 `ipconfig` 找本机 IPv4 地址；Windows 防火墙可能还需要放行 8443（见 `docs/LAN-TESTING.md`）。

#### 4.1.1 先做一次预检（在碰手机之前）

服务端与客户端的对接问题**可以在这台电脑上先验完**，不必等手机：

```powershell
cd <项目目录>\protocol
$env:GOWORK='off'
$env:SCHAT_RELAY_URL='https://127.0.0.1:8443'
go test ./mobile/ -run LiveRelay -v
```

- [ ] 输出 `--- PASS: TestPublishAndFetchAgainstALiveRelay`

它会发布整池预密钥、连取两次（必须拿到两个**不同**的一次性预密钥）、用服务端真正返回的 JSON 建立会话、双向加解密、然后撤回。

> **为什么值得先跑**：这一条曾经抓到过一个真实缺陷——客户端把预密钥包 PUT 到了集合路径而不是 `/api/v1/keys/{identity}`，服务端回 `404`，于是**发布从来没成功过**。若没先跑这一步，双机测试会卡在"建立会话"上，而现象只会像"对方没上线"。

若这一条不通过，**手机那边一定也过不了**，请把输出发我。

#### 4.1.2 再验一次客户端的网络层（同样不必碰手机）

上面那条只走了服务端与协议核心。客户端真正用来连服务器的是 `:core` 里的 OkHttp 实现（TLS 固定 + WebSocket），它是另一条独立的路：

```powershell
cd <项目目录>\android
.\gradlew.bat :core:test "-Pschat.relayUrl=https://192.168.1.100:8443"
```

> **参数必须加引号。** PowerShell 5.1 会把 `-Pschat.relayUrl=…` 从点号处拆开，交给 Gradle 一个裸的 `.relayUrl=https://…`，然后 Gradle 报
> `Cannot locate tasks that match '.relayUrl=https://...'`——这个报错看起来像 Gradle 的问题，其实不是。写成 `"-Pschat.relayUrl=https://…"`。

- [ ] 输出中 `RelayLiveTest` 的 4 项全部 PASS（而不是 SKIP）

它验证四件事：

| 用例 | 证明什么 |
|---|---|
| 固定指纹连接被接受、订阅被应答 | OkHttp 真的走了我们的固定信任管理器，WebSocket 升级成功，命令格式被服务端接受 |
| 用 IP 连接时主机名校验不误杀 | 证书里只写了别的名字也不影响——因为**指纹才是身份**，这一条曾是个真实的坑 |
| 错指纹被拒绝 | 固定**确实在执行**，不是摆设 |
| 自签名但未配置指纹被拒绝 | 唯一绝不能连的组合被挡住了 |

> **不加 `-Pschat.relayUrl` 时这 4 项会 SKIP 而不是失败**，这样普通的 `:core:test` 保持离线可复现。如果你看到的是 SKIP，说明参数没传到。
>
> 这两条预检加起来覆盖了「服务端 ↔ 协议核心」与「客户端网络层 ↔ 服务端」两段。**剩下的只有安卓特有的部分**（Conscrypt 的 TLS 实现、Android Keystore 包装），而那部分原理上只能在真机上验——这正是第 4.2 节之后要做的事。

> 让两台设备用**同一条 URI** 是这一节的重点之一：如果两台设备的 `fp` 不同，说明服务器的自签名证书每次重启都在重新生成（`--state-dir` 没配对），这一点必须排除。

### 4.2 在两台设备上完成引导

- [ ] 设备 A：走完第 3 节的 ①–⑤，服务器填上面那条 URI
- [ ] 设备 B：同样走完，服务器填**同一条** URI
- [ ] 两台都进入会话（「聊天」页点联系人，或「通讯录」里点名字），对话顶部都显示元数据警告（红色竖线 + 一行小字，占据一条窄带）
- [ ] 两台的状态行都不再是"连接错误"

> 两台设备的「我的身份」**必须不同**。若相同，说明引导时复用了同一份保险库（例如从同一台机器恢复），必须先清除数据重来。

### 4.3 建立会话

记 **A 的身份**（点「显示我的完整身份」，64 位十六进制），填入 **B** 的输入框。

- [ ] B 填入 A 的身份，点「获取预密钥并建立会话」
- [ ] B 的状态行变成「已发送会话请求」然后「会话已建立」
- [ ] B 的界面上出现**安全码**（60 位数字）
- [ ] A 的界面**也**出现安全码（A 是响应方，它的身份从握手消息中得到）

> ⚠️ **如果 A 没有出现安全码**，那说明 `PeerIdentity` 这条链路有问题，请把两台的 logcat 都发我。这一项是本次新增代码里最容易出问题的地方。

### 4.4 比对安全码（这一步才是真正的身份验证）

**当面或通过可信渠道**逐组比对两台设备显示的安全码。

- [ ] 两台的安全码**逐位完全相同**
- [ ] 故意在一台上改一位再比对，能立刻看出不同（用来确认你们真的在看这个数字，而不是走形式）

> **为什么必须比对**：服务器在发布预密钥时**不校验身份**，任何人都能以任意身份密钥覆盖别人的条目。如果你不比对安全码，一次服务器作恶或投毒就能让攻击者完全冒充对方，而应用不会有任何提示——从密码学上那段会话是完全"合法"的。安全码是这条链上唯一不依赖服务器的环节。

### 4.5 收发消息

- [ ] A 发一条 `hello from A`，B 收到，内容与时间正确
- [ ] B 回复一条，A 收到
- [ ] 连续快速发 10 条，全部到达且**顺序正确**
- [ ] 发一条很长的消息（> 1000 字），到达且内容完整
- [ ] 发一条含**中文、emoji、换行**的消息，到达后内容完全一致
- [ ] 发送方每条消息下显示「已送达服务器」（**不是**"已读"——本架构无法知道对方是否已读）

### 4.6 断线与离线

- [ ] 让 A 切到飞行模式，B 发一条消息 → B 应显示「对端离线，消息未送达（服务器不存储）」
- [ ] A 恢复网络，**不应**自动收到那条消息（`live` 模式就是不存，这是设计意图而不是缺陷）
- [ ] 让 A 切到飞行模式再恢复，B 再发一条 → A 能正常收到（棘轮在断线后继续工作）

> 如果你想验证 `buffer` 模式（服务器在内存里暂存），用 `--mode buffer` 重启服务器再试一次：这时 B 应显示「已暂存在服务器内存中」，A 上线后能收到。

### 4.7 重启后继续（棘轮状态持久化）

- [ ] 两台都从最近任务里划掉 SCHAT
- [ ] 重新打开，各自解锁
- [ ] A 发一条消息 → B **能解密**（说明棘轮快照被正确保存与恢复）
- [ ] 关掉服务器再打开两台 → B 发消息应报连接错误，而不是假装成功

> 若第 3 项失败（重启后收不到），说明 `chat.session.<peer>` 快照没有正确写入或恢复。请提供 logcat。

### 4.8 出问题时的排查顺序（首次真机测试踩到的坑）

**第一条：两台手机必须连在同一个 Wi-Fi 上，不能用移动数据。**

`192.168.x.x` 是私有局域网地址，手机走 4G/5G **永远到不了**它。这一条看起来很显然，但它在第一次真机测试里正是失败原因，而且报错完全不指向它。

**用手机浏览器 30 秒判定网络是否通**（比看 App 报错快得多）：

在手机的浏览器里打开

```
https://192.168.1.100:8443/api/v1/health
```

- 看到证书警告（自签名，正常）→ 继续 → **能显示一段 JSON** = 网络通，问题在别处
- **打不开 / 超时 / 无法访问** = 手机到不了服务器，先解决网络（是否同一 Wi-Fi？是否开了 AP 隔离？主机名是否写成了公网地址？）

| App 里的现象 | 含义 | 先检查 |
|---|---|---|
| `Software caused connection abort` / `failed to connect` / `timed out` | 手机到不了中继 | 手机是否在用**移动数据**；是否与服务器同一 Wi-Fi |
| `发布预密钥失败：…` | 本机没有成功登记 | 上一行的连接是否正常；服务器是否在运行 |
| 对方显示 `HTTP 404: no bundle published for that identity` | **对方从未成功发布**（不是你的问题） | 对方那台的连接状态是否显示「已订阅信箱」 |
| 对方显示 404，而对方的连接状态看起来正常 | **服务器重启过**，或对方装的是旧版 APK | 见下方「服务器重启」 |

**服务器一旦重启，所有预密钥包都会消失。** 中继的预密钥目录**只在内存里**（这是设计意图：服务器不落盘），`--state-dir` 持久化的只有证书。所以：

- 每次重启服务器后，**两台设备都必须重新发布一次**。13:10 及以后的版本会在**每次连上服务器时自动重发**，所以你只要等它自动重连（或重开 App）即可；更早的版本必须杀掉 App 重开。
- 如果你在旧版本上遇到"对方明明在线却一直 404"，先怀疑这一条，而不是怀疑加密。

| `获取预密钥失败` 且身份填错一位 | 同样会得到 404 | 让对方点「显示我的完整身份」，**逐字符**复制 64 位，不要凭截图手抄 |

**状态行的读法**（0.1.0-alpha 起，报错不再覆盖状态行）：

| 状态行 | 含义 |
|---|---|
| `预密钥已发布` | 中继已接受你的包，对端可以找到你 |
| `已连接` → `已订阅信箱` | WebSocket 已建立且订阅成功 |
| `连接已断开，N 秒后重试（第 M 次）` | 正在自动重连（退避 2/4/8/16/30 秒）。**不需要杀 App 重开** |

两边都应该先看到「已订阅信箱」，再去建立会话。

### 4.10 换机恢复（恢复码 + 备份）

这一步验证本次新增的恢复路径。它需要 **A 机（已有身份）** 与 **B 机（新装或清过数据）**。

**在 A 机上：**

- [ ] 「我的 → 恢复码」能看到 24 个词，点「复制恢复码」成功
- [ ] 点「复制备份」，提示「备份已复制（N 字符）」——那段文本应以 `SCHAT-BACKUP-1` 开头
- [ ] 把恢复码抄在纸上、把备份文本粘贴到别处（备忘录／发给自己）

**在 B 机上：**

- [ ] 走完引导（新口令、新身份——此时身份与 A 机不同）
- [ ] 「我的 → 恢复码」，把备份文本粘进第一个框、24 个词粘进第二个框，点「从备份恢复」
- [ ] 出现确认弹窗后点「替换」，随后应**回到解锁页**
- [ ] 用 B 机自己的口令解锁，进「我的」——**身份缩写应与 A 机一致**
- [ ] 「通讯录」里应看到 A 机的联系人
- [ ] 用 B 机给 A 机的对端发一条消息，对端能收到并解密

**错误路径（至少试一条）：**

- [ ] 故意把某一个词改错 → 提示「恢复码与备份不匹配，或备份已损坏」，且**不做任何替换**
- [ ] 只输入 23 个词 → 「从备份恢复」按钮不可点

> **预期会失去的两样东西**（这是设计，不是缺陷）：
> 1. **聊天记录不随备份走**——旧消息用旧会话的密钥加密，新设备没有对应棘轮状态；
> 2. **预密钥会重新生成**——一次性预密钥只在旧设备上有效，重发会被中继发给两个人。

## 6. 这一版已知的不足（不必当作缺陷报告）

| 项 | 说明 |
|---|---|
| 一组会话只能有一个联系人 | 界面一次只处理一段会话；多联系人属于后续步骤 |
| 元数据保护未启用 | 信箱地址由公开身份派生，界面上有常驻警告；内容仍端到端加密 |
| 无群聊 | 步骤 6a/6b（MLS） |
| 无媒体消息 | 步骤 7，目前只支持文本 |
| 消息历史保存在本机保险库 | 无云端同步，换机需靠恢复码（还原流程尚未实现） |
| 安全码只能显示，不能标记"已确认" | 尚未持久化"我已核对过"这一状态 |
| debug 签名、R8 关闭 | 仅自测；正式包需另建签名并验证 keep 规则 |
| `x86`（32 位）无原生库 | 仅影响 32 位模拟器 |
| 会话控制器无自动化测试 | `:app` 模块依赖协议 AAR，无法在 JVM 上测；只能靠真机验证 |
