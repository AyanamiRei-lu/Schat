# SCHAT 中继服务器接口

> 本文档是**客户端与服务端之间线协议的权威描述**。
> 两端的实现必须与本文一致：服务端在 `server/internal/gateway` 与 `server/internal/directory`，客户端在 `android/core/.../net/`。

**服务端二进制**：`schat-server`（单文件、零第三方依赖、零数据落盘）
**传输**：TLS（默认自签名 + 客户端固定指纹），HTTP/1.1

---

## 1. 端点总览

| 方法 | 路径 | 作用 | 是否需要会话 |
|---|---|---|---|
| `GET` | `/ws` | WebSocket 升级，收发信封 | 否 |
| `GET` | `/api/v1/health` | 健康检查与指标摘要 | 否 |
| `GET` | `/api/v1/config` | 公开配置（名称、协议版本、指纹） | 否 |
| `PUT` | `/api/v1/keys/{identity}` | 发布或替换自己的预密钥包 | 否 |
| `GET` | `/api/v1/keys/{identity}` | 获取对端预密钥包（**消费一个一次性预密钥**） | 否 |
| `DELETE` | `/api/v1/keys/{identity}` | 撤回自己的预密钥包 | 否 |

**没有"登录"端点**，因为**没有账号**。身份由客户端本地生成的密钥对定义；中继不知道你是谁，也不需要知道。

## 2. `/ws` —— 信封收发

### 2.1 升级

标准 RFC 6455 握手，服务端用纯标准库实现（见 `server/internal/ws`）。协商子协议 `schat.v1`（可选）。

服务端强制拒绝：

| 违规 | 结果 |
|---|---|
| 未掩码的客户端帧 | 关闭 1002（RFC 6455 §5.1 强制要求） |
| 设置了 RSV 位（未协商扩展） | 关闭 1002 |
| 控制帧被分片或超过 125 字节 | 关闭 1002 |
| 文本帧非合法 UTF-8 | 关闭 1007 |
| 单条消息超过 `limits.max_envelope_size + 1024` | 关闭 1009 |

> **HTTP/2 被禁用**：WebSocket 升级依赖连接劫持，HTTP/2 做不到。服务端把 ALPN 固定为 `http/1.1`。

### 2.2 客户端 → 服务端：控制消息（文本帧，JSON）

```json
{"t":"sub","tokens":["<32 位十六进制>", ...]}
{"t":"unsub","tokens":[...]}
{"t":"hb"}
```

| 字段 | 说明 |
|---|---|
| `t` | `sub` 订阅信箱 / `unsub` 取消 / `hb` 心跳 |
| `tokens` | 投递令牌，16 字节的十六进制（32 字符）。**单次最多 256 个** |

订阅是**能力制**：谁持有令牌谁就能往该信箱投递。服务器不知道令牌属于谁。

### 2.3 客户端 → 服务端：信封（二进制帧）

```
token (16 字节) ‖ 载荷
```

**服务端只读前 16 字节**用于路由，其余部分原样转发，不解析、不存储、不解密。这一点由架构保证：服务端模块**禁止导入协议核心**（`tools/verify.ps1` 机械校验）。

**载荷的内部结构由客户端定义**，当前为：

```
token(16) ‖ 内容类型(1) ‖ 内容
  0x01  0x01 = SCS-1 加密帧（header 43 字节 + 密文）
  0x02  0x02 = 会话握手 Init（138 字节明文，仅含公钥）
```

> 握手 Init 在线上是明文，这是**设计而非疏漏**：它只含公钥，其真实性来自被折进双方根密钥的 transcript 绑定（`SCHAT.md` §4.4）。任何人都能读，但没人能伪造出双方都会接受的那一条。

### 2.4 服务端 → 客户端

**二进制帧**：与投递时**逐字节相同**的信封（含 token，便于接收方知道是哪个信箱收到的）。

**文本帧**（JSON 回执）：

| `t` | 含义 | 附带字段 |
|---|---|---|
| `ok` | 订阅/退订成功 | — |
| `hb` | 心跳回应 | — |
| `delivered` | 已转发给 N 个在线连接 | `n` |
| `queued` | 收件人离线，已存入内存队列（仅 `buffer` 模式） | — |
| `offline` | 收件人离线，**未存储**（`live` 模式） | — |
| `err` | 帧被拒绝 | `m`（原因） |

> `offline` 与 `queued` 是**刻意区分**的。`live` 模式下拒绝而不是静默丢弃——让发送方以为消息已送达是最危险的谎言。

### 2.5 两种投递模式

| 模式 | 离线时 | 磁盘痕迹 |
|---|---|---|
| **`live`（默认）** | 回 `offline`，**什么都不存** | 零 |
| `buffer` | 回 `queued`，存内存队列（TTL 默认 72h，单信箱上限 100 条） | 零（仅 RAM，重启即丢） |

两种模式**都不落盘**。服务器没有数据库依赖，也没有可写数据目录。

## 3. `/api/v1/keys/{identity}` —— 预密钥目录

### 3.1 为什么需要它

SCS-HSK 握手的第一步是发起方取得响应方的 `PreKeyBundle`（身份公钥 + 签名预密钥 + 一个一次性预密钥）。两个从未通信过的客户端唯一都能访问的就是中继。

### 3.2 发布（`PUT`）

请求体（JSON）：

```json
{
  "identity_signing": "<64 位十六进制>",
  "identity_agreement": "<64 位十六进制>",
  "signed_pre_key": "<64 位十六进制>",
  "signed_pre_key_id": 1,
  "signed_pre_key_signature": "<128 位十六进制>",
  "one_time_pre_keys": [
    {"id": 1, "public": "<64 位十六进制>"},
    {"id": 2, "public": "<64 位十六进制>"}
  ]
}
```

校验：各字段必须是**正确长度的十六进制**，否则 `400`。函数式校验见 `directory.Bundle.Validate`。

响应：`200 {"identity":"<归一化后的身份密钥>"}`

> ⚠️ **身份必须同时出现在路径里**：`PUT /api/v1/keys/{identity}`。
>
> 服务端 `ServeHTTP` 在检查 HTTP 方法**之前**就要求路径中存在身份，路径为空一律返回 `404 no identity key in the path`——**即使请求体里带着 `identity_signing`**。把包 PUT 到 `/api/v1/keys/` 是个很容易犯的错，而它的症状极具误导性：发布静默失败，唯一的真实表现是"没有任何对端能联系上这个客户端"，看起来就像"对方一直没上线"。
>
> 这个错误在本项目的客户端里**真实发生过**（`DirectoryClient.publish` 曾 PUT 到集合路径），由下面的真实服务器往返测试抓出，现已修复并在 `:core` 里加了钉死 URL 形状的单元测试：
>
> ```powershell
> # 终端 1：启动中继
> cd server; $env:GOWORK='off'
> go run ./cmd/schat-server --listen 0.0.0.0:8443 --name dev --state-dir .\state
>
> # 终端 2：对一个真实服务器跑往返
> cd protocol; $env:GOWORK='off'
> $env:SCHAT_RELAY_URL='https://127.0.0.1:8443'
> go test ./mobile/ -run LiveRelay -v
> ```
>
> 该测试会：发布整池 → 连续取两次 → 断言两次拿到**不同**的一次性预密钥 → 用服务端真正返回的 JSON 建立会话 → 双向加解密 → 撤回条目。
> 它存在的理由是：纯单元测试只能拿客户端**自己镜像的**字段名去校验自己，两边同时错就会一起通过。

### 3.3 获取（`GET`）

```json
{
  "identity_signing": "...", "identity_agreement": "...",
  "signed_pre_key": "...", "signed_pre_key_id": 1,
  "signed_pre_key_signature": "...",
  "one_time_pre_keys": [ {"id": 7, "public": "..."} ]
}
```

**最多返回一个一次性预密钥，且返回即从池中移除**（在同一把锁下完成）。

> **为什么这一点是安全关键**：一个被发给两个发起方的一次性预密钥就不再是"一次性"，而"首条消息的前向保密"整个论证都建立在它之上。`directory_test.go` 里有一条并发测试：16 个 goroutine 抢 200 个预密钥，断言**每个恰好被发放一次**。

池耗尽时返回**不含**一次性预密钥的包。这是**降级而非错误**（`SCHAT.md` §4.4）：会话仍能建立，只是首条消息失去前向保密，发起方会从标志位看到这一点。

### 3.4 ⚠️ 客户端必须做的两件事（服务端无法代劳）

**发布没有认证**——没有账号可以认证，所以**任何人都能以任意身份密钥发布或覆盖预密钥包**。服务端无法阻止，加一个服务端检查只会制造虚假的安全感。

因此客户端**必须**：

1. **确认 `identity_signing` 等于自己请求的那个身份**。否则被覆盖的条目可以塞进攻击者自己的密钥并"验证通过"。这一步在协议绑定层强制（`mobile.EstablishSession` 的 `peerIdentityHex` 参数）。
2. 验证签名预密钥的签名——由 `protocol.EstablishSession` 完成。

最终的防线是**60 位安全码线下比对**（§5）。

### 3.5 生命周期

| 项 | 值 |
|---|---|
| TTL | 30 天（`directory.DefaultTTL`） |
| 容量上限 | 10000 个身份（`directory.DefaultMaxIdentities`） |
| 单包上限 | 64 KiB |
| 存储位置 | **仅内存**，进程退出即全部消失 |

## 4. 健康检查

```
GET /api/v1/health
```

```json
{
  "status": "ok",
  "version": "0.1.0-alpha",
  "protocol": "SCS-1/v1",
  "mode": "live",
  "storage": "none",
  "uptime_seconds": 12.3,
  "live_connections": 2,
  "fingerprint": "<64 位十六进制证书指纹>",
  "prekey_directory": {
    "identities": 3,
    "one_time_prekeys": 297,
    "note": "public key material only; held in RAM, never written to disk"
  },
  "unimplemented": ["..."]
}
```

`unimplemented` 字段**刻意保留**：它列出本版本尚未实现的功能，避免任何人把半成品当成完整的服务器。

## 5. 客户端连接信息格式

服务器启动时打印：

```
schat://connect?h=<主机>&p=<端口>&n=<名称>&fp=<证书指纹>&ss=1
```

| 参数 | 含义 |
|---|---|
| `h` | 客户端要拨的地址 |
| `p` | 端口（默认 8443） |
| `n` | 显示名称 |
| `fp` | **证书指纹（SHA-256，64 位小写十六进制）** |
| `ss` | `1` 表示自签名证书，客户端**必须**固定指纹 |

**解析规则**（`core/ServerConfig.kt`）：

- 拒绝未知参数（防止 `http=` 这类笔误静默生效）
- 拒绝重复参数
- **拒绝"自签名但无指纹"**——这是唯一会让人毫无察觉地连到攻击者的组合

### 5.1 二维码负载格式

两种码，都是 `schat://` URI，因此永远不会互相混淆：

| 码 | 负载 | 在哪里扫 |
|---|---|---|
| **身份码** | `schat://id?i=<64 位十六进制身份公钥>` | 聊天界面 →「扫码」 |
| **服务器连接码** | `schat://connect?...`（即 §5 那条 URI，**原样传递**） | 首次引导 →「配置服务器」→「扫码」 |

扫描器**也接受裸的 64 位十六进制**，这样任何工具生成的码都能用。

解析实现于 `core/qr/QrPayload.kt`，**校验职责刻意不重复**：身份码只做长度与十六进制校验；连接码原样交给 `ServerConfig.parse`，由它给出"缺少证书指纹"这类具体错误，而不是笼统的"这不是 SCHAT 的码"。两份校验定义迟早会不一致，而先跑到的那份会静默取胜。

> **服务端为什么不打印二维码**：在服务端渲染二维码需要一个第三方库，而"服务端零第三方依赖"是一条被 `tools/verify.ps1` **机械校验**的架构保证（见 §1 与 `SECURITY.md`）。因此**第一台设备仍需粘贴一次 URI**；此后每台设备都可以扫第一台设备上「服务器连接码」显示的码，不必再碰键盘。
>
> **二维码不证明任何身份。** 扫到的只是对方屏幕上显示的那串字符，与手抄完全等价——唯一的收益是**不会抄错**。而这一点并非小事：抄错一位十六进制所产生的报错，与"对端从未发布过预密钥"**逐字相同**，两种原因无法从现象上区分。真正的身份验证仍然是 60 位安全码的线下逐组比对（见 §5 与 `docs/DEVICE-TEST.md` §4.4）。

## 7. 本版本尚未实现

| 项 | 影响 |
|---|---|
| 配置二维码 | 需手动粘贴连接 URI（步骤 3c） |
| 群聊（MLS） | 步骤 6a/6b |
| 媒体分块传输与 P2P 直连 | 步骤 7 |
| 真机双机对发验证 | 控制器与界面已实现并通过编译，但尚未在两台真机上走通 |

> **元数据保护的状态（重要）**：投递令牌机制（§2.2）已在服务端完整实现，但客户端**尚未实现令牌的会话内交换**——那是先有鸡还是先有蛋的问题（首次通信前没有会话可以交换令牌）。
>
> 因此当前版本的客户端**临时**由公开身份派生信箱地址：
>
> ```
> mailbox = SHA-256("schat-mvp-mailbox" ‖ identity_signing)[0:16]
> ```
>
> 实现位于 `protocol/mobile/mailbox.go` 的 `MailboxToken`，而不是 Kotlin 侧。原因是收发两端必须算出**同一个值**（发方用于寻址、收方用于订阅），两份独立实现发生漂移时不会报错，只会让握手永远收不到——这类静默失败值得用一份共享定义加一条钉死的黄金向量测试来避免（见 `TestMailboxTokenIsPinned`）。
>
> 该妥协**放弃** `SCHAT.md` §4.7 的元数据保护：拿到某人身分公钥的人即可算出其信箱地址并观察其流量时间模式。**内容仍受端到端加密保护**——信箱是地址，不是密钥。客户端界面上有一条常驻警告横幅说明这一点，且该横幅由状态标志驱动，令牌交换落地后删掉它是与修复绑定的单点改动。
