# 昵称（微信式自报名）设计

> 状态：**待确认**。本文不含产品代码；确认后才进入实施计划。
>
> 日期：2026-10-31
> 适用版本：`0.1.0-alpha` 之后

---

## 1. 意图与为什么

现在的 SCHAT 只有一种名字：**本机备注**（`Contact.nickname`，只存在本机，对方不知道）。
好处是谁也不能在别人的列表里改名；代价是每台设备看到的都是自己起的名字，群里认不出人时
只能显示身份缩写。

要的是微信那套：**每个人给自己起一个名字，别人看得到；你仍然可以给他起备注，备注盖过昵称。**

用户明确要求：群里即使两个人从没单聊过，也要能看到对方的昵称。

---

## 2. 目标

1. 「我的」页可以设置 / 修改 / 清除自己的昵称，随时生效。
2. 昵称能到达：**好友（会话）列表、聊天页标题、通讯录、群成员名单、群标题**。
3. 显示优先级：**本机备注 > 对方昵称 > 身份缩写**。
4. 群成员即使与本机没有一对一会话，也能拿到昵称。
5. 昵称**不经过服务器明文**，不进入预密钥目录。
6. 昵称随换机备份走（自己的）；对方的昵称可以重新学到。

## 3. 非目标

- **不做群昵称**（每个群单独一个名字）。用户说的是「类似微信名」，即全局一个名字。
  群昵称是纯增量，将来可以加，不改变本次的数据结构。
- **不做昵称唯一性 / 抢注 / 认证**。谁都能自称任何名字，微信也一样。
  昵称是标签，不是身份；身份仍由安全码与身份公钥定义。
- **不做服务器侧的名片目录**。那会让服务器读到名字，推翻「服务器读不懂」的前提。
- 不做「昵称历史」「昵称变更通知」这类消息，聊天记录里不会出现「某某改名为某某」。

## 4. 反目标（做到了也算失败）

- 把昵称放进预密钥包 / 握手明文 → 任何拿到身份公钥的人（含服务器）都能读到名字。
- 昵称能注入换行 / 制表符，伪造出第二条联系人记录或第二条群成员记录。
- 昵称被当作身份判断依据（例如「名字一样就是同一个人」）。
- 为了显示昵称而让服务器知道「谁和谁在同一个群」之外的新元数据。

---

## 5. 命名模型

| 名字 | 存在哪 | 谁写的 | 优先级 |
|---|---|---|---|
| 备注（remark） | 本机联系人记录 | 我 | 最高 |
| 昵称（nickname） | 本机「对方名字簿」 | **对方自己** | 中 |
| 身份缩写 | 由身份公钥算 | 无 | 兜底 |

代码里现在的 `Contact.nickname` **就是备注**。为了避免歧义，本次：

- `Contact.nickname` 保留原义（备注），**不改字段名、不改编码格式**（避免迁移与降级丢数据）；
- 新增 `Contact.peerName`：**派生字段，不写进联系人编码**，打开联系人时由名字簿填入；
- `Contact.displayName = nickname.ifBlank { peerName.ifBlank { abbreviate(identityHex) } }`。

这样现有所有调用点（会话行、聊天页、通讯录、加人候选）自动获得新优先级，不需要逐个改。

## 6. 线协议：昵称通告

### 6.1 两个新的信封内容类型

| 类型 | 名称 | 载荷 | 去向 |
|---|---|---|---|
| `0x06` | 单聊昵称通告 | SCS-1 加密帧（`text` AEAD 档） | 对端身份信箱 |
| `0x07` | 群昵称通告 | MLS `PrivateMessage`（与 `0x03` 同一套加密） | 群信箱 |

**为什么必须两个类型**：接收方要**先知道用哪套机器解密**。`0x03` 与 `0x01` 已经因为
这个理由分开（见 `protocol/mobile/groupwire.go` 的注释）；昵称通告同样不能靠「解开再看」。

### 6.2 载荷格式（两种类型共用）

```
SCHAT-NICK-1\n<base64(昵称 UTF-8)>
```

- 版本行固定；不认识的版本**丢弃**，不猜。
- base64 是防注入，不是美化：昵称是用户输入，换行/制表符会破坏行格式。
- 上限：整段载荷 ≤ 256 字节；昵称本身按 `ContactCodec.MAX_NICKNAME_LENGTH`（64）截断，
  并沿用 `sanitiseNickname`（去掉 ISO 控制字符 + trim）。
- **空昵称合法**，表示「清除」：对方回退到身份缩写。

### 6.3 发送时机

单聊（`0x06`）：

1. **会话建立完成时**：发起方在 `startSessionWith` 成功装好会话后发一次；
   响应方在 `acceptHandshake` 完成后发一次。双方因此各拿到对方的名字。
2. **打开一段已有会话时**：如果本连接还没向这个对端通告过，发一次。
3. **自己改昵称时**：发给**当前会话的对端**，以及自己所在的每个群（见下）。

> 已知取舍：改昵称不会立刻推给所有联系人——只有当前会话的对端与所有群会即时收到；
> 其余联系人在你下次打开与他的会话时同步。理由见 §6.7（本机一次只持有一段活动会话）。
> 这是 v1 的诚实边界，写进文档而不是假装没有。

群（`0x07`）：

1. **自己入群后**（`processWelcome` 成功）：向群发一次，让已有成员认识你。
2. **处理一条提交、发现有新成员加入时**：向群发一次，让新成员认识你。
3. **自己改昵称时**：向每个群各发一次。
4. **连接建立后**：对每个群发一次（每条连接至多一次），补上离线期间错过的通告。

### 6.4 接收与校验

单聊 `0x06`：

```
ContentType(wire) == 0x06 → 用【当前活动会话】DecryptProfile → 解析载荷
  → 成功：把名字写进名字簿，key = 当前会话的对端身份
  → 解析失败：丢弃并计数，不弹错误（对方可能只是版本更新）
```

群 `0x07`：

```
unwrapGroupProfile → header(message) → 取该群的 stateJson → GroupOpen
  → 得到 senderLeaf 与明文 → 解析载荷
  → 用 members(stateJson) 把 senderLeaf 映射成 identity
  → 写名字簿（key = identity）
```

**为什么群这条路能跨过「没单聊过」**：名字由成员自己用 MLS 密封，任何持有该 epoch 的成员
都能解开；它不需要一对一会话，也不需要服务器参与。

**为什么不需要在载荷里附带身份**：MLS 的 sender leaf 已经由 epoch 的机制认证；用群状态把
leaf 映射成身份，比让对方在载荷里自报身份更强。若 leaf 在当前状态里找不到（说明本机还没
应用那条提交），密文本来就解不开——两者是同一个前提。

### 6.5 发出的两条硬规则

**① 回执必须占位。** 中继对**每一封**信封恰好回一次 `delivered/queued/offline/err`，而客户端
按发送顺序把回执配给「待确认投递」队列（`PendingDelivery.Message/Handshake/Group`）。昵称通告
如果直接发而不占位，它的回执会被配给**前面某条聊天消息**，把一条其实没送达的消息标成
「已送达」。所以新增 `PendingDelivery.Profile`（群通告共用同一个占位），只发不结算。

**② 先落盘、再发送。**

- 单聊：加密会推进发送链。`EncryptProfile` 之后**立即** `persistSession(peer)`，否则重启会
  复用链密钥。
- 群：`GroupSeal` 会推进 generation。**先**把新 generation 写进存储，**再**发送；发送失败也
  不回退——代数用掉就是用掉了（见 §9）。

### 6.6 失败与重发

- 通告是**幂等**：收到同样的名字不会产生消息、不会改变排序、不会加未读。
- `live` 模式下对端离线 → 通告丢失，**不做无限重试**；下次会话建立 / 下次连接 / 下次打开
  会话时自然重发。
- 不做「昵称待发送队列」：它会把一个纯标签变成需要持久化的投递状态，收益不匹配成本。

### 6.7 为什么单聊通告只走活动会话

`ChatController` 现在只保持**一段活动会话**（`active`），这是已知的单会话限制。收到
`0x06` 时没有发送者标识可用来选会话（信封里刻意没有），试图对每个联系人依次试解会在
每次收包时做 O(联系人) 次棘轮解包，并可能推进/回滚多份快照——代价与风险都不成比例。

所以：单聊昵称在**会话建立**与**打开会话**时交换，足够覆盖「联系人都是聊过的人才存在」
这一事实。群通告不受此限制。

## 7. 本机存储

### 7.1 名字簿（新）

- key：`peers.names`
- 内容：一行一个 `身份十六进制<TAB>base64(昵称)`，上限 500 条，超出丢弃最旧的。
- 解码：任何一行坏掉就跳过该行；不因一行坏掉而丢整本。
- 写入：收到通告时 upsert；**后到的覆盖先到的**（昵称是标签，不做版本仲裁）。
- 删除：联系人删除时**不删**名字（群里还要用）；提供「清空名字簿」只在恢复/清数据时由
  整个保险库删除完成。

### 7.2 自己的昵称

- key：`profile.nickname`（可选）。
- `ClientProfileStore` 的必填项**不变**——旧档案没有这一项仍然算完整。
- 读写新增 `loadNickname()` / `saveNickname()`；空串等价于未设置。

### 7.3 备份

`ProfileBackup` 增加 `nickname: String = ""`，`ProfileBackupCodec` 增加一行
`name=<base64>`：

- 编码总是写这一行（空串也写），保持格式稳定；
- 解码时该行**缺失视为空**，因此旧备份仍可恢复，新备份在旧版本上只是忽略这一行。

### 7.4 群成员名

`GroupRecord.memberNames`（按叶子下标）**不再作为显示来源**：叶子下标每次成员变更都会变，
而它是本机历史遗留。群成员名改为：

```
自己（identity == 我的身份）  → 我的昵称（未设置则「我」），后接「（我）」标记
其他成员                       → 联系人备注（若该身份在联系人里）
                              → 名字簿昵称
                              → 身份缩写
```

`GroupRecord.memberNames` 本次不删（协议与存储不动），但界面不再读它；将来可清理。

## 9. 前置修复（P0，独立于昵称但必须先做）

**群消息的 `generation` 从未推进。**

- `GroupSeal` 返回 `NextGeneration`（`protocol/mobile/groupmessage.go`）；
- `ChatController.sendGroup` 只取 `MessageHex`，`NextGeneration` 被丢弃；
- `GroupStore.save` 只在入群（0）与处理提交（0）时写入 generation；
- 因此同一 epoch 内所有群消息都用 generation 0。

**影响**（按代码里的注释，不是推断）：每次发送都带新的 `reuse guard`，nonce 不会重复，
所以**不是** two-time-pad；但发送者的棘轮密钥在一个 epoch 内被反复使用，等于放弃了
该 epoch 内「每条消息一代密钥」的前向保密，并且违反 §9.2（用过的代数应删除）。
昵称通告也要消耗 generation，不修就会把同一个问题扩大到控制消息上。

**修法**：

1. `prepareGroupMessage` 返回 `nextGeneration`；
2. `sendGroup` 在**发出之前**把新代数写进存储（新增 `GroupStore.saveGeneration`，
   避免重写整个状态 JSON）；即使发送失败也不回退——代数用掉就是用掉了；
3. 群昵称通告走同一套；
4. 补一个 `:core` 测试：连续两次 `saveGeneration` 后读回的是第二次的值；再补一个
   Go 侧测试证明同 generation 两次 seal 会被拒绝（若核心有这个守卫）或至少记录现状。

> 这一项会改动群消息发送路径。**建议单独一步、先做、单独验证**，不要和昵称混在一个提交里。

## 10. 安全与隐私

| 问题 | 结论 |
|---|---|
| 服务器能看到昵称吗 | 不能。单聊在 SCS-1 密文里，群聊在 MLS 密文里，都不经过预密钥目录 |
| 昵称能防冒充吗 | **不能**。任何人可以自称任何名字。这是设计取舍，必须写进 SECURITY.md 与界面文案 |
| 昵称能当身份用吗 | 不能。安全码、身份公钥、验证状态都不受昵称影响 |
| 群里的昵称会泄露群成员关系吗 | 不增加新泄露：它走的是本来就存在的群信箱；服务器仍只看到「某 token 有条目」 |
| 恶意昵称能做什么 | 长度上限 + 控制字符剥离，防止破坏行格式、防止双向覆盖字符伪装；不能注入记录 |
| 收到伪造昵称通告会怎样 | 只有持有对应会话/epoch 密钥的人能构造，所以「谁能改我的名字」与「谁能给我发消息」是同一批人 |

`SECURITY.md` 需新增一条已知边界：**自报名未经认证**。

## 11. 测试计划

纯 JVM（`:core`）：

- 名字簿：编码/解码往返、坏行跳过、上限、重复身份后到覆盖、空名字清除；
- 显示优先级：备注 > 昵称 > 缩写（含备注为空串、昵称为空串、两者都空）；
- 联系人编码兼容：**7 字段旧记录仍能解码**，8 字段不存在（`peerName` 是派生字段）；
- 备份兼容：带 `name=` / 不带 `name=` 都能解码；空名字往返；
- 载荷编解码：往返、超长拒绝、非法 base64 拒绝、错误版本拒绝、控制字符被清洗。

Go（`protocol/mobile`）：

- `0x06` / `0x07` 的 wrap/unwrap 往返；
- **类型混淆必须失败**：`0x06` 当 `0x03`、`0x07` 当 `0x01`、`0x01` 当 `0x06` 全部报错；
- 截断信封、空载荷、尾随字节；
- 未认证/篡改的群通告解不开。

`tools/verify.ps1` 与 CI：沿用现有门禁；**AAR 必须重建**（新增导出面），构建约 5 分钟。

真机（手工，写入 `docs/DEVICE-TEST.md`）：

1. A 设昵称「阿狸」→ B 的通讯录/会话列表/聊天页出现「阿狸」；
2. B 给 A 设备注「老张」→ B 侧全部显示「老张」，A 侧仍显示自己设的「阿狸」；
3. A 清空昵称 → B 侧（B 未设备注时）回退为身份缩写；
4. A 建群拉 B、C；B 与 C 从未单聊 → B 的群成员名单里出现 C 的昵称；
5. A 改昵称 → 群成员名单立即更新；
6. 两台手机对同一人显示不同名字时，安全码仍一致（昵称不影响身份）。

## 13. 需要你拍板的事

1. **群昵称**：本次不做（全局一个名字）。如果你要「每个群单独一个名字」，现在说，
   存储结构会不同（名字簿要按 (群, 身份) 存）。
2. **昵称长度上限**：我按现有备注的上限取 **64 字符**（中文 64 字），比微信的 16 字宽。
   要更短的话现在说。
3. **改昵称的传播范围**：v1 是「当前会话对端 + 所有群即时，其余联系人下次打开会话时同步」。
   要做到「立刻推给所有联系人」需要多会话并行收发，属于另一项架构改动。

## 14. 留给实施者判断的部分

- 弹窗的排版与措辞（沿用 `Components.kt` 的既有零件）；
- 名字簿的键名与文件内的具体转义（只要保持 base64 + 行格式 + 上限）；
- `0x06`/`0x07` 的 Go 函数命名（建议 `WrapProfile` / `UnwrapProfile` /
  `WrapGroupProfile` / `UnwrapGroupProfile`，与现有 `WrapGroup` 对称）；
- 是否在「我的」页显示昵称的首字母头像（现状头像固定为 "S"，可以顺带改成昵称首字母，
  但这是可选项）。
