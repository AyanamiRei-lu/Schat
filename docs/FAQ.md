# 常见问题（FAQ）

## 这是不是又一个"自己发明加密算法"的项目？

不是，而且我们明确拒绝那样做。

SCHAT **没有发明任何密码学原语**。X25519、Ed25519、HKDF-SHA256、ChaCha20-Poly1305、AES-256-GCM、Argon2id、BLAKE2b 全都是公开标准算法。

我们原创的是**协议组合层**：密钥调度（LEXSORT 角色无关拼接 + transcript 入盐）、未认证帧的回滚防护、分块密钥梯与哈希树、按文件格式分化的 AEAD 矩阵、投递令牌元数据保护、双因子保险库。这些是工程与协议设计。

这是 Signal、WhatsApp、Wire 等所有严肃加密通信产品的共同做法，也是密码学界唯一认可的做法。详见 `SCHAT.md` 第 11.1 节。

## 算法都公开了，为什么还不能破解？

因为安全性从来不依赖算法的保密（Kerckhoffs 原则，1883 年提出）。

所有密钥都是 256 位，密钥空间是 2²⁵⁶ ≈ 1.16 × 10⁷⁷。即使攻击者掌握全部源码、完全控制服务器，他面对的仍然是这个空间。现实中唯一的攻击路径是**猜口令**，而 SCHAT 用 Argon2id（每次猜测约 0.5 秒 + 64 MiB 内存）加上 Keystore 设备绑定来抬高这条路径的成本。

**但我们必须诚实**：没有任何算法能抵御"用户设置 123456"。详见 `docs/THREAT-MODEL.md` 第 5 节。

## 服务器真的看不到我的消息吗？

看不到，而且这是**架构保证**而不是政策承诺：

- 服务端 Go 模块**禁止导入**协议包，二进制里根本没有解密代码（可用 `go list -deps ./server/...` 自行验证）
- 不引入任何数据库依赖，没有可写的数据目录
- `live` 模式（默认）下服务器连内存队列都不创建——一个不存在的类型无法泄漏数据
- 信封里不含发送者标识，投递令牌每 24 小时轮换

## 服务器重启后消息会丢吗？

会，这是**设计意图**。

- `live` 模式：对方不在线就直接告知发送方"未送达"，服务器什么都不存
- `buffer` 模式：消息只在**内存**里等待，最长 72 小时，进程重启即全部消失，磁盘上从来没有过

如果消息绝不能丢，请使用 `live` 模式并接受"对方离线则发送失败"的行为。

## 换手机后聊天记录还能恢复吗？

只有在**同时**满足以下两个条件时：

1. 你抄写了 24 个单词的恢复码（首次启动时引导）
2. 你导出了加密备份并保存在自己控制的地方

因为服务器不保存任何数据，**没有任何人**能帮你恢复账号或聊天记录。这是"数据不上云"的必然代价。

## 群聊安全吗？

群聊使用 **IETF MLS (RFC 9420)**，具备完整的前向保密与后妥协安全，成员被移除后 epoch 立即推进。这是当前群组加密的最高标准，没有做任何安全妥协。

**但有一个诚实的边界**：MLS 的投递服务（也就是你的服务器）能看到"哪些客户端在拉取同一个群的密文"，即**群成员关系对服务器可见**。这不是实现缺陷，是 RFC 9420 的架构性质。隐藏这一点需要匿名化投递服务，属于 v2 研究项。

## 为什么不用我自己的密码算法？

因为无法验证。

一个密码学原语要被认为安全，需要全球密码学界**数十年**的攻击尝试。历史上每一个"军事级自研加密算法"在公开后都被迅速攻破。自己造的 S 盒几乎必然存在设计者无法发现的代数弱点，而且**你没有任何办法知道自己错了**——错误的加密算法照样能正常加解密，只是不再安全。

如果你坚持要自研原语，请先阅读 `SCHAT.md` 第 11.6 节的风险说明。

## 现在能用吗？

**不能。** 当前是 `0.1.0-alpha`，处于工程骨架阶段：

- ✅ 密码学基础层与协议核心已实现并通过测试（含 RFC 5869 与 RFC 6455 官方测试向量）：会话建立、双棘轮、乱序/重放/篡改/反射防护
- ✅ 中继服务端可运行且**网关已实现**（实测 10.6 MB 内存），两个真实客户端可经它互发密文
- ❌ 群聊（MLS）、文件传输、客户端网络层与聊天 UI 都还没实现

进度见 `SCHAT.md` 第 13.2 节的步骤清单，或 App 首屏的"构建状态"页面。

## 代码经过安全审计吗？

**没有。**

在通过独立第三方密码学审计之前，请不要用于高价值机密信息或高风险场景。审计完成后会在 README 顶部公示报告链接。

## 为什么用 AGPL-3.0？

为了保证 SCHAT **永远是开源且免费的**。

AGPL 的关键条款是：任何修改后的版本如果对外提供网络服务，必须同样开源。这阻止了"拿 SCHAT 搭一个闭源商业服务"的情况。如果你需要在自己的闭源产品里使用 SCHAT 的代码，AGPL 不允许——这是刻意的。

## 我可以自己搭服务器吗？难吗？

可以，而且目标是**两分钟**。

```bash
curl -fsSL https://get.schat.dev | sh
schat-server --domain chat.example.com
```

服务端是单个 Go 二进制，无数据库、无 Redis、无消息队列、无反向代理要求，配置文件可以完全不写。启动后打印二维码，手机扫码即完成配置。

（注：自动 TLS 与二维码渲染在路线图步骤 3 实现；当前 `--print-uri` 已可用。）

## 为什么服务端的配置文件用 JSON 而不是 YAML？

为了保持**零第三方依赖**。

YAML 需要一个第三方解析库，JSON 不需要（`encoding/json` 属于标准库）。服务端的目标是"单二进制、零依赖、低占用"，多一个依赖就多一份供应链风险和体积。十来个配置项用 JSON 完全够用。

## App 为什么要读取那么多权限？

它**不**读取。SCHAT 在 manifest 里只申请两个权限：

| 权限 | 用途 | 能否拒绝 |
|---|---|---|
| `INTERNET` | 连接你自己配置的服务器 | 不能（否则无法收发） |
| `CAMERA` | 扫二维码以交换身份公钥 | **能**——拒绝后仍可手动输入 |

**相机只在你打开扫码界面时启用**，画面在内存中解码后立即丢弃，不保存、不拍照、不上传。它存在只是因为手抄 64 位十六进制身份公钥太容易出错——而抄错一位产生的报错，与"对方从未发布过预密钥"**完全相同**，两种原因无法从现象上区分。

没有通讯录、没有定位、没有通话记录、没有短信、没有设备标识符、没有麦克风。读取媒体（照片/视频/文件）与麦克风权限会在步骤 7 实现对应功能时才申请。
