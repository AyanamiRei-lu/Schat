# SCHAT 威胁模型

> 本文档说明 SCHAT **防得住什么、防不住什么**。安全产品最大的危险是让用户产生错误的安全感，因此本文件宁可写得刺眼，也不写得好看。
>
> 设计依据：[`../SCHAT.md`](../SCHAT.md) 第 6 节与第 11 节。

---

## 1. 资产

| 资产 | 价值 | 存放位置 |
|---|---|---|
| 消息明文 | 高 | 仅通信双方的设备内存 / 本地加密库 |
| 媒体文件明文 | 高 | 同上 |
| 身份私钥 | 极高 | Android Keystore（可选 StrongBox 硬件） |
| 会话密钥（棘轮状态） | 极高 | 仅内存，用后擦除 |
| 本地保险库密钥 | 极高 | 内存（由口令 + 设备密钥派生） |
| 通讯录 / 群成员 | 中高 | 仅本地加密库 |
| 元数据（谁和谁通信） | 中 | **部分暴露**，见第 4 节 |
| 投递令牌 | 低 | 每 24 小时轮换 |

## 2. 信任假设

SCS-1 的设计以下列假设为前提。若某条不成立，对应的防护也随之失效。

| 假设 | 若不成立 |
|---|---|
| 服务端**不可信**，可能被入侵、取证或强制配合 | 无影响：服务端本来就读不懂内容，这是设计的核心 |
| Android 系统与 Keystore 实现可信 | 设备密钥可能被提取，第二道防线失效 |
| 客户端的随机数来源（`crypto/rand`）可信 | 密钥可预测，一切失效 |
| 用户通过带外渠道验证过联系人身份 | 存在中间人风险（UI 显示"未验证"警告） |
| 用户的安装包未被篡改 | 攻击者可植入后门，端到端加密无意义 |
| 用户使用了足够强的口令 | 见第 5 节 |

## 3. 攻击者能力矩阵

| 攻击者 | 能力 | 结果 |
|---|---|---|
| **被动网络窃听者**（同一 Wi-Fi 的攻击者） | 抓包 | ❌ 无法解密内容。可观察到流量大小与时间 |
| **恶意/被入侵的中继服务器** | 完全控制服务端进程、内存、磁盘 | ❌ 无法解密。服务器二进制内**不存在**解密代码，也没有任何长期密钥 |
| **执法取证服务器** | 拿到服务器全部数据 | ❌ 一无所获：服务器不落盘、不建库（`live` 模式下甚至不排队） |
| **窃取手机文件系统** | 拿到加密数据库文件 | ❌ 无法解密：需要口令 **且** 需要 Keystore 中的设备密钥 |
| **窃取数据库 + 已知口令 + 未 root 设备** | 可调用 Keystore | ❌ 设备密钥标记为不可导出 |
| **窃取数据库 + 已知口令 + 已 root 且可调用 Keystore** | 可代理 Keystore 调用 | ⚠️ **可能解密**。这是 Android 平台安全模型的上限，非本应用缺陷 |
| **主动中间人**（篡改握手） | 替换公钥 | ❌ 会话建立失败（transcript 绑定）；未验证时 UI 告警 |
| **重放攻击者** | 重发旧密文 | ❌ 拒绝：计数器 + 已见集合 |
| **篡改媒体分块的中继** | 修改/重排/删除分块 | ❌ 检测：分块哈希树 |
| **流量分析者**（ISP / 国家级） | 全网观测 | ⚠️ **部分有效**：内容安全，但通信关系可通过时序与 IP 关联推断 |
| **物理胁迫** | 强迫用户交出设备与口令 | ❌ 无法防御。缓解：阅后即焚、紧急销毁 |
| **恶意接收方** | 对方截图、转发、泄露 | ❌ 无法防御：端到端加密保护传输，不保护接收端 |

## 4. 元数据：明确的边界

这是最容易被误解的部分，因此单独说明。

**SCS-1 隐藏的**：

- 服务器不知道消息是谁发的（信封中不含发送者标识）
- 服务器不知道邮箱属于谁（投递令牌每 24 小时轮换，与身份无关联）
- 服务器不知道文件类型、文件名、文件大小（填充到标准桶）

**SCS-1 不隐藏的（v1）**：

| 暴露项 | 原因 | 缓解 |
|---|---|---|
| 连接来源 IP 与连接时长 | TCP/TLS 层固有 | 用户自行配置 SOCKS5/HTTPS 代理或 Tor |
| 数据包大小与发送时序 | 网络层固有 | 长度填充降低了精度，但无法消除 |
| 在线/离线状态 | 路由需要 | 无 |
| **群成员关系** | **MLS (RFC 9420) 架构决定投递服务可见"哪些客户端拉取同一个群的密文"** | v1 接受并明确告知；匿名化 DS 列为 v2 研究项 |

> 关于群成员关系：这不是实现缺陷，而是 RFC 9420 的架构性质。要做到"连服务器都不知道群里有谁"，需要匿名化投递服务方案，学术界仍在演进。SCHAT v1 **不做虚假承诺**。

## 5. 口令：真正的攻击面

攻击者不会穷举 2²⁵⁶ 的密钥空间，他们会**猜口令**。SCS-1 的三道防线：

| 防线 | 机制 | 攻击者代价 |
|---|---|---|
| 内存硬 KDF | Argon2id，默认 64 MiB / t=3 / p=2 | 单次猜测约 0.5 秒且占 64 MiB，GPU 并行优势被内存带宽掐死 |
| 设备绑定 | 保险库密钥需要 **口令 AND Keystore 设备密钥** | 只有数据库文件 + 口令**仍然解不开** |
| 长口令引导 | 强制 ≥10 字符，检测常见弱口令，提供随机生成器 | 把口令熵从约 20 位拉到 70 位以上 |

> **没有任何算法能抵御"用户设置 123456"。** 我们能做到的是把每次猜测的成本抬高到 0.5 秒 + 64 MiB，并叠加设备绑定。这是工程现实，不是免责声明。

## 6. 前向保密与后妥协安全

| 场景 | 单聊（SCS-DR） | 群聊（MLS） |
|---|---|---|
| 长期身份密钥泄露 | ✅ 无法解密历史消息（前向保密） | ✅ 同左 |
| 当前会话密钥泄露 | ✅ 棘轮推进后自动恢复（后妥协安全） | ✅ Commit 后自动恢复 |
| 成员被移除 | — | ✅ epoch 推进，被移除者无法解密后续消息 |
| 一次性预密钥耗尽 | ⚠️ 暂时失去首条消息的完整前向保密，通过 flags 位告知 | 不适用 |

## 7. 供应链

| 依赖 | 风险 | 处置 |
|---|---|---|
| Go 标准库 | 平台级信任 | 不可消除 |
| `golang.org/x/crypto` | 唯一的第三方密码学依赖 | 官方维护、广泛审计、版本锁定 |
| Android 平台 | 系统级信任 | 不可消除 |
| Gradle 插件链（AGP/Kotlin/Compose） | 构建期代码执行 | 版本锁定在 `libs.versions.toml` |
| **无其他运行时依赖** | — | 已最小化：无分析 SDK、无广告 SDK、无网络框架 |

## 8. 已知未修复项

| 项 | 影响 | 状态 |
|---|---|---|
| 未经第三方密码学审计 | 可能存在未知实现漏洞 | 文档显著标注，欢迎审计 |
| MLS 尚未实现 | 群聊功能不可用 | 步骤 6a |
| 会话层与棘轮层尚未实现 | 单聊功能不可用 | 步骤 2 |
| WebSocket 网关与 TLS 尚未实现 | 无法实际收发 | 步骤 3 |
| 客户端网络层与聊天 UI 未实现 | 还发不出消息（协议与服务端已就绪） | 步骤 4–5 |
| 后量子（ML-KEM）未启用 | 无法抵御未来量子计算机 | v2；标准库已具备 `crypto/mlkem` |
